## Header grid lines restored, and a page-wide scroll-restore race fixed (2026-09-18)

Two real bugs, both reported by the user and reproduced/fixed with hard measurements, not guesses.

**1. Header's vertical grid lines had gone invisible.** Root cause: `Header.tsx`'s `bg-background/60 backdrop-blur-md` (added 2026-09-17) sits IN FRONT of `BackgroundLines.tsx`'s header-band column lines, which are `rgba(255,255,255,0.02)` — already barely-there at full opacity. A 12px backdrop blur smears that already-tiny contribution across a much wider area and the 60%-opacity dark tint on top finishes the job: confirmed via a Playwright pixel check (forced the header-band lines to solid opaque red — zero visible pixels through the header; the identical override one row below, outside the blurred header, painted cleanly). Fixed by moving the header-band `ColumnLines` instance to be a CHILD of `<header>` itself (rendered in `Header.tsx`, not `BackgroundLines.tsx`) — children of an element paint on top of that element's own background/backdrop-filter, so the lines now render above the blur instead of behind it, at the same weight as the rest of the page's grid. `BackgroundLines.tsx` no longer renders anything in the header band (dead code removed, comment left explaining why); `ColumnLines` and `HEADER_HIDE_WIDE`/`HEADER_HIDE_NARROW` are now exported from `BackgroundLines.tsx` for `Header.tsx` to reuse.

**2. Refreshing anywhere on the page could snap you into the middle of MachineSection's zoom sequence, even from the footer.** Root cause, found by grepping across the codebase (not assumed): EVERY pinned section — Hero, Infrastructure intro, Machine, Pricing, Build — carried its OWN independent copy of the "restore scrollY after StrictMode/SSR-spacer churn" fix (`scrollYBeforeChurnRef` + a 100ms `setTimeout` correction), each captured inside that section's OWN `useGSAP` effect. Those five effects run in DOM order within the same commit — Hero's runs first and collapses Hero's own SSR-reserve spacer (shrinking the document), which can immediately clamp `window.scrollY` (ScrollTrigger's own layout reads force a synchronous reflow) BEFORE Infrastructure's effect ever runs. So Infrastructure captured an already-clamped value, Machine captured an even-more-clamped one after both Hero's and Infrastructure's spacers had collapsed, and so on through Pricing and Build. Each of those five stale captures then fired its own corrective `window.scrollTo` ~100ms later — whichever fired LAST won, regardless of where the user actually was. Machine's own capture (taken after two prior spacers had already collapsed) was frequently still "wrong" by the time its timeout fired, dragging the page back into its own huge pin range no matter the real scroll position — exactly the reported symptom.

Fixed by deleting all five per-section copies and replacing them with ONE shared `src/components/layout/ScrollChurnGuard.tsx`, mounted once in `layout.tsx` (right before `<BackgroundLines />`). It captures `window.scrollY` via a `useState(() => window.scrollY)` LAZY INITIALIZER — which runs during this component's first RENDER, and React fully renders the whole tree before any component's effects run — so this capture is guaranteed to happen before any section's spacer has had a chance to collapse and clamp it. One restore (150ms later, comfortable margin past five sequential collapses settling) replaces all five races. (A first attempt read/wrote a plain `useRef` during render, which works in practice but trips the `react-hooks/refs` lint rule — refs are formally meant to be read/written outside of render; `useState`'s lazy initializer is the sanctioned "compute once" mechanism instead.) Verified via Playwright: reload at 5 scattered scroll fractions (0.15/0.35/0.55/0.75/0.95 of document height) — all five restore to the exact pre-reload `scrollY`, delta 0. Reload mid-way through Machine's zoom sequence (scrollY ~9300, well inside its pin) — restores exactly, screenshots before/after are pixel-identical in content. Reload scrolled all the way to the footer — stays at the footer, does not snap back into Machine.

**Related, found while diagnosing the above — Hero's 3D server model could visibly "pop" from closed to open right after a refresh.** `HeroServerModel.tsx`'s GLB loads asynchronously and always starts at `setProgress(0)` (closed) — it has no way to know the scroll-derived target itself. The existing fix (`onReady` → `ScrollTrigger.refresh()`) re-syncs `self.progress` correctly, but `heroScrollAnimation.ts`'s timeline uses `scrub: 1` (a full second of eased catch-up) — so that re-sync visibly animated the model from closed to its true open pose over about a second instead of it just already being there, reported as "instead of open, I find it closed, then it suddenly opens, like a bug." Fixed by adding a `modelSyncRef` (filled in by `useHeroScrollAnimation` once its timeline exists) that HeroSectionClient.tsx's `handleModelReady` calls instead of `ScrollTrigger.refresh()` directly: it still calls `ScrollTrigger.refresh()` (recompute pin positions) but then also calls `tl.progress(tl.scrollTrigger.progress)` — setting the timeline's progress directly jumps it immediately and still fires every tween's `onUpdate` (so the model's `setProgress` still gets called with the correct value), it just skips the scrub's eased interpolation. Verified via Playwright: reloaded at scrollY 700 and 1000 (mid- and near-end of the disassemble range) — the model's very first rendered frame after the GLB loads already matches the exact `--stack-gap`/pose a normal (non-refreshed) scroll to that same position produces, byte-for-byte on the CSS custom property and visually identical on screenshot; no intermediate wrong pose is ever rendered, and the value is rock-stable afterward (30 samples over 4.5s, no drift). BuildSection's own `HeroServerModel` instance did NOT need the same fix — its ScrollTrigger uses `scrub: true` (immediate, no eased number), which has no catch-up delay to pop through.

**Follow-up, same day — `ScrollChurnGuard` itself could fight real user input.** User report, reproduced exactly with Playwright: refresh while scrolled to the footer, then immediately scroll UP toward Hero — the hero server showed closed, then suddenly opened, then closed again. Root cause: `ScrollChurnGuard`'s restore compared `window.scrollY` to its captured target and just fired `window.scrollTo` unconditionally 150ms later — with no way to tell "scrollY drifted because layout churned" apart from "scrollY changed because the user is actively scrolling." A wheel-scroll test starting the instant `domcontentloaded` fired showed the real sequence: scrollY correctly followed the user's wheel input for the first couple of samples, then — right at the 150ms mark — jumped back to the ORIGINAL footer position, because the restore fired and `scrollY !== target` was still true. From the hero server's point of view that read as exactly the report: mid-transition, then suddenly forced back to "fully open" (footer is past hero's whole pin range), then closing again as the user's continued scrolling caught back up.

First fix attempt — cancel the restore on any `wheel`/`touchstart`/scroll-key event, listeners attached from inside `ScrollChurnGuard`'s own `useGSAP` effect — turned out to still be too late: a Playwright repro starting wheel events the instant `domcontentloaded` fires can beat React's own hydration, so the effect never gets a chance to attach its listeners before the first genuine input arrives, and the restore fires unopposed anyway (confirmed: the footer-snap-back was still there). Moving listener-attachment into a `next/script strategy="beforeInteractive"` (`layout.tsx`'s `SCROLL_CHURN_GUARD_SCRIPT` — injected into the initial HTML, runs before any Next.js/React code, before hydration can even begin) closed that gap — but broke the PASSIVE (no-scroll) case instead: capturing `window.scrollY` that early can predate the browser's own history scroll-restoration finishing, so `target` got captured as near-0 garbage instead of the real prior position, and every restore silently no-op'd (current scrollY already "matched" the wrong target) — confirmed via a 5-position passive-reload sweep, every single one landed thousands of px short of its target.

Final fix is a two-part split, each half doing only the job it's reliably early/late enough for: the `beforeInteractive` script (`layout.tsx`) ONLY arms a global `window.__scrollChurnCancelled` flag on the first `wheel`/`touchstart`/scroll-key event — nothing else, so there's no target-capture accuracy to get wrong. `ScrollChurnGuard.tsx` (the React component, `useState(() => window.scrollY)` lazy initializer during render, same as before) still owns capturing the accurate target and performing the actual restore, just checks `window.__scrollChurnCancelled` instead of attaching its own (too-late) listeners, and calls `window.__scrollChurnCleanup?.()` to remove them once its own 150ms window closes. Verified via Playwright, both scenarios in the same run: the 5-position passive sweep restores exactly (delta 0 on all five) — AND the wheel-race repro (footer refresh, wheel scroll starting immediately) shows a clean, monotonic `--stack-gap` sequence (open the whole time the raw churn-clamp jump is still resolving, since that lands past hero's own pin end either way, then a smooth, single, uninterrupted close as scrollY approaches 0) — no snap-back, no open→close→open flicker. Zero console/page errors across the whole sequence.

**Fourth bug in the same family, found the same day from a follow-up user report**: "footer-ზე მივედი, refresh ვქენი, მერე ზემოთ ავედი — hero section-ში server დახურული დამხვდა, თუმცა ღია უნდა ყოფილიყო". Reproduced precisely: reload while scrolled to the footer, wheel-scroll straight up to a point still within Hero's pin (scrollY ~1100, well past the disassemble tween's own end) — `--stack-gap` (the CSS custom property) correctly read `140px` (fully open), but the actual GLB mesh rendered CLOSED. This is the exact "CSS var right, 3D pose wrong" split the second bug's fix (reading `disassemble.t` directly) was supposed to prevent — so something was UNDOING that direct sync afterward. Root-caused with instrumented logging (temporarily traced every `HeroServerModel.setProgress` call back to its caller via `new Error().stack`, removed once diagnosed): the sync's own `setProgress(1)` call landed correctly, immediately followed — same tick — by FOUR more `setProgress(0)` calls, all originating from the disassemble tween's OWN normal `onUpdate` callback, not from anything Hero's code called directly.

The actual source: `BuildSectionClient.tsx`'s `handleModelReady` (for its own, entirely separate `HeroServerModel` instance near the page's bottom) calls the STATIC `ScrollTrigger.refresh()` — which refreshes EVERY ScrollTrigger on the page, not just Build's own. Hero's own ScrollTrigger has `invalidateOnRefresh: true`, so ANY such page-wide refresh — triggered by Hero's own GLB finishing, Build's, or anything else — makes GSAP briefly reset Hero's animated properties to their natural/un-animated state to re-measure them. Since Hero's and Build's GLBs are both small and typically both already cached, they tend to finish loading within the same handful of milliseconds, so Build's unrelated refresh call was landing right after Hero's own sync and undoing it, with nothing left to correct it afterward (the page had stopped scrolling, so no further real scroll event would ever re-trigger the normal onUpdate path).

Two changes: (1) removed Hero's OWN `ScrollTrigger.refresh()` call from `modelSyncRef` entirely — nothing about a GLB parsing actually changes the pin's start/end (the wrapper's CSS box size is independent of whether the 3D model has loaded), so it wasn't buying anything, and removing it at least stops HERO's own copy of this self-inflicted reset. (2) Rather than trying to coordinate every other section's own present-or-future `ScrollTrigger.refresh()` calls (fragile — Build's isn't the only one that could exist), `modelSyncRef`'s sync is now defensively re-asserted three times: once immediately, once on the next `requestAnimationFrame` (catches a same-tick refresh, exactly what the repro showed), and once more after a 300ms `setTimeout` (catches a slower GLB elsewhere on the page). All three read `disassemble.t` fresh at call time, so each is correct regardless of what happened between them. Verified via Playwright with the exact repro (reload at footer, wheel-scroll to scrollY ~1100) — the GLB mesh screenshot now matches the CSS var and a normal (non-refreshed) scroll to the same position; re-ran the full passive 5-position sweep, the wheel-race snap-back check, and a normal top-to-1200px scroll sanity check together — all pass, zero console/page errors.

## Background grid: mouse deformation + grid-drawn cross marks (2026-09-20)

Built to the plan in `background-line-animations.md` — read that file's §10 for the measurements
and the places the plan turned out to be wrong. Short version of what changed here:

- **The grid is now drawn twice over.** `CssGridLines` (split out of `BackgroundLines.tsx`, takes a
  colour) is the first paint and the permanent fallback; `GridCanvas.tsx` puts a WebGL2 canvas over
  it that draws the identical grid and bends it around the cursor. The canvas sets
  `data-grid-canvas="on"` on the wrapper only after it has drawn a frame, and one plain CSS rule in
  `globals.css` hides the fallback off that attribute — so there is never a frame with two grids
  and never one with none. No WebGL2, or a lost context, and the page is exactly what it is today.
  Raw WebGL2, not three.js: this layer is on every page and always on, and the whole thing is a
  fullscreen triangle plus one shader (its own lazily-imported 8.5 KB chunk, no new dependency).
- **Effect**: `pull`, radius 220, strength 16, easing 0.12 — chosen in the lab, living in
  `src/lib/gridEffect/config.ts`. All lengths are design px, scaled by `--s` like everything else.
- **An idle page draws zero frames** (measured by patching `drawArrays`). The rAF loop stops itself
  once the eased cursor has caught up; the `pointermove` listener is passive and only records a
  position; reduced motion and coarse pointers never attach it at all.
- **`src/lib/grid.ts` is now the single source of truth for both sides** — it gained the hidden
  column sets (moved out of `BackgroundLines.tsx`, `Header.tsx` imports them from there now) and the
  numeric helpers `gridMetrics()` / `columnCenterX()` / `rowTopY()` / `nearestColumn()` /
  `nearestRow()`, so the CSS and the shader cannot drift.
- **The "+" crosses are grid intersections now, not `cross.svg` images.** `useGridMarks(anchor,
  {gapX, gapY})` snaps four marks around an element's box and the shader draws them as short
  brighter segments of the very column and row they sit on — so they bend with the lines and they
  cannot be off-grid at any viewport width. Measured at 33 widths, 1280→2560: worst distance from
  the exact line **0.227px**. This retires the whole grid-snap → cube-relative → "just delete them"
  saga documented further down; do NOT restore the old `GridCross`/`CardCross` code from those
  entries — use the hook.
  - Machine section: same 4 corners as before (`gapX: 60, gapY: 70`), same fade, `crossRefs` gone.

## Conventions established

- **Shared content inset — superseded 2026-09-16**: no longer `mx-auto max-w-[1722px] px-6 lg:px-[99px]`. Now pure `vw`-fluid: horizontal insets expressed as `vw` derived from a `1920` reference (e.g. `5.15625vw` for the `99px`-at-1920 content edge inset), applied uniformly at every viewport width with no breakpoint gating — see `Header.tsx`'s `paddingLeft`/`paddingRight` and `BackgroundLines.tsx`'s `INSET_VW` for the pattern. Reuse *this* for any new section, don't reintroduce the old `max-w` convention — it caused a real, user-reported bug (grid/header drifting apart, asymmetric margins) on non-1920 screens. If a section ever needs Figma-derived px positions inside its own content, convert with the same `vw(px) = (px / 1920) * 100 + 'vw'` helper, or a fraction (`px / referenceWidthPx`) if it needs to live inside an SVG/`objectBoundingBox` mask.
